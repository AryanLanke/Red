## How a session works (always the same)
1. The user opens a new session (Sonnet 5.5, Medium) in D:\RED and pastes: `You are track A. Read D:\RED\red\plan.md and do the next part.` (or track B). Or nobody pastes: `python D:\RED\red\scripts\run_tracks.py` runs these sessions headless, A and B side by side, round after round (3 by default), and stops a track when it ticks nothing. The summary is in `D:\RED\cache\tracks\<date>\summary.md`, and a `D:\RED\cache\tracks\STOP` file stops it after the running sessions. A headless session can't ask the user anything: if a part needs the user, do what can be done without them, write the question under the part, and stop without ticking it.
2. Read this whole file. Then check **Flaws I noticed** below: an open flaw in your track comes before any part.
3. Take the **first unchecked part of your track** (`- [ ]`). Do only that one part. Never start a second part in the same session.
4. Work in your track's folder: track A in `D:\RED\worktrees\track-a`, track B in `D:\RED\worktrees\track-b`. If the folder doesn't exist, create it from main: `git -C D:\RED\red worktree add D:\RED\worktrees\track-<x> -b track-<x> origin/main`. Start with `git fetch` and `git rebase origin/main`.
5. **Commit after every small working step** (`type(scope): what`, message written to a file, then `git commit -F <file>`) and push your branch (`git push origin HEAD:track-<x>`). Many small commits are wanted.
6. When the part works:
   1. Run `git fetch` and `git rebase origin/main`.
   2. Run the **full** test suite:
      ```
      $env:RED_HOME="D:\RED"; $env:QT_QPA_PLATFORM="offscreen"; $env:QT_QPA_FONTDIR="C:\Windows\Fonts"
      D:\RED\.venv\Scripts\python.exe -m pytest tests -q -p no:cacheprovider --basetemp=D:\RED\cache\pytest-tmp-<x>
      ```
   3. Push to main: `git push origin HEAD:main`.
7. In this file, tick the part (`- [x]`) and add one line under it: the date, the commit hashes, what was measured, and anything the user should try. Commit and push that to main too.
8. Stop. Say in 3–5 lines what was done and what the user should try. The user closes the session and opens a new one for the next part.

If a part is too big for one session, finish a clean piece of it, commit, and split the rest into a new unchecked part right below it. Don't leave work uncommitted.

### How the model gets trained (A5 and A8–A10, in plain words)
Training is the hardest part, so it goes in small steps, and only after the tests exist: without them nobody can tell whether a trained model is better. Most of today's problems (dropped requests, the slow extra routing call, needless web searches) are code, not the model, and training won't fix them.
1. **What we train:** not a new brain. A small add-on (a LoRA) on top of the same Qwen3.5-4B Red uses now. It teaches three things: talking like a person, with each companion in its own style; picking the right tool; and telling "this is for me" from "not for me". Facts about the user stay in memory, never in the model.
2. **Where the examples come from:** (a) the simulated user (A5) talks to each companion for hundreds of short conversations; (b) the user's own real sentences from `logs\commands.jsonl`, their side only, with Red's answers written fresh; (c) a few dozen hand-picked "perfect" replies per companion. Every example is graded by the A5 rules. Only the good ones are kept (about 2,000–5,000), and private details are scrubbed.
3. **Where it trains:** Kaggle's free GPU (16 GB, about 30 hours a week), once the user has added `kaggle.json`. This laptop's RTX 4050 (6 GB) is too tight for it while Red's own model is loaded. Unsloth makes a 4B LoRA run take about 1–2 hours. The notebook (A8) explains every cell, and `scripts/kaggle_train.py` (A9) runs it without the browser.
4. **Coming back:** the result is one GGUF file (q4_K_M, about 2.5 GB), imported into Red's own Ollama under a new name. The old model stays, so switching back is one setting.
5. **Is it better?** Run the same simulated conversations, the replay tests, the routing check and the blind "who said this" test on the old and new models. Switch only if it's more human, at least as good at tools, and not slower. Otherwise, write down what was wrong, fix the data, and train again.
